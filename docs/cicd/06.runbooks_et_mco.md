# 🚑 6. Runbooks de Survie & Maintien en Conditions Opérationnelles (MCO)

> **Objectif de ce chapitre :** Documenter mes procédures opérationnelles de diagnostic rapide (**Triage en 30 secondes**), mes **5 Runbooks de dépannage** pour les pannes critiques de l'infrastructure (Vault scellé, Tunnel SSH & conflit de port, saturation mémoire `OOM Killer`, erreurs Prisma et incidents Web/CI-CD), ainsi que mes automatisations de **Maintien en Conditions Opérationnelles (MCO)** : renouvellement SSL Certbot, rotation des secrets Vault, sauvegardes quotidiennes PostgreSQL avec Plan de Reprise d'Activité (PRA) et hygiène Docker/Ubuntu.

## 🧭 6.1. Réflexes de Diagnostic Rapide (Triage en 30 secondes)

En cas d'anomalie sur l'une de mes URLs publiques (`app`, `api`, `staging`, `docs`), j'exécute systématiquement ces **4 commandes** sur le VPS (`ssh ubuntu@51.210.101.236`) pour identifier immédiatement le composant défaillant :

```bash
# 1. Vérifier l'état de santé de tous les conteneurs (Up / Restarting / Exited)
sudo docker ps -a --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"

# 2. Inspecter les logs en direct d'un conteneur précis (ex: API Prod)
sudo docker logs -f --tail 100 dsr-api-prod

# 3. Vérifier l'état du Reverse Proxy Nginx sur l'hôte
sudo systemctl status nginx --no-pager
sudo tail -n 50 /var/log/nginx/error.log

# 4. Vérifier la charge RAM / Swap / Disque NVMe du VPS
free -h && df -h /
```

## 🛠️ 6.2. Les 5 Runbooks Opérationnels (Guide de Survie)

### 🔐 Runbook 1 : HashiCorp Vault Scellé (`Vault Sealed`)

#### 🚨 Symptômes
*   L'API NestJS (`dsr-api-prod` ou `dsr-api-staging`) redémarre en boucle (`Restarting`) ou renvoie une erreur `502 Bad Gateway` via Nginx.
*   Les logs de l'API affichent une erreur `503 Vault is sealed` lors de la récupération des secrets au démarrage.
*   **Cause fréquente :** Le VPS OVH a redémarré (maintenance ou `sudo reboot`), ou le conteneur `dsr-vault` a été recréé par Docker Compose. Par design (Zéro-Trust), Vault se verrouille automatiquement dès qu'il perd son état en RAM.

#### 🔧 Résolution pas-à-pas
1.  **Vérifier le statut de Vault :**
    ```bash
    sudo docker exec -it dsr-vault vault status
    ```
    Si la ligne indique `Sealed: true`, il faut fournir le quorum de **3 clés Unseal sur 5** (récupérées depuis ma sauvegarde locale chiffrée).

2.  **Déverrouiller le coffre (protéger les clés entre guillemets `""` pour éviter l'interprétation des caractères `/` ou `+` par Bash) :**
    ```bash
    # Clé 1 (Progression : 1/3)
    sudo docker exec -it dsr-vault vault operator unseal "LeaINa4YV/************************AKihVTQH"

    # Clé 4 (Progression : 2/3)
    sudo docker exec -it dsr-vault vault operator unseal "eS/Ff4Wc5S************************+K7AtclsVrN"

    # Clé 5 (Progression : 3/3 -> Déverrouillage effectif : Sealed = false !)
    sudo docker exec -it dsr-vault vault operator unseal "s5gweW5A3e************************sqmtGLnSmEg"
    ```

3.  **Redémarrer immédiatement les APIs si elles étaient en attente (*backoff* Docker) :**
    ```bash
    sudo docker restart dsr-api-prod dsr-api-staging
    ```

### 🐘 Runbook 2 : Connexion pgAdmin & PostgreSQL de Production (Tunnel SSH)

#### 🚨 Contexte
Les ports `5050` (pgAdmin) et `5432` (PostgreSQL) sont volontairement liés à `127.0.0.1` sur le VPS et bloqués par le pare-feu UFW. Il est donc normal de ne jamais pouvoir y accéder directement via l'IP publique du serveur.

#### 🔧 Procédure de connexion sécurisée (Depuis mon PC local)
1.  **Ouvrir le tunnel SSH chiffré dans un terminal local :**
    ```bash
    ssh -L 5050:localhost:5050 -L 5432:localhost:5432 ubuntu@51.210.101.236
    ```
    *(Laisser cette fenêtre ouverte pendant toute la durée de l'intervention).*

> [!WARNING]
> **Astuce Conflit de Port Local (`Address already in use`) :**  
> Si mon PostgreSQL de développement local tourne déjà sur le port `5432` de mon PC, le tunnel sur `5432` échouera ou redirigera silencieusement vers ma base locale ! Dans ce cas, je mappe le tunnel sur le port local **`5433`** :
> ```bash
> ssh -L 5050:localhost:5050 -L 5433:localhost:5432 ubuntu@51.210.101.236
> ```
> Il suffit alors d'utiliser `localhost:5433` dans mes outils locaux (DBeaver, Prisma CLI).

2.  **Accéder à l'interface Web pgAdmin (`http://localhost:5050`) :**
    *   **Host name/address :** `dsr-postgres` *(résolution DNS interne au réseau Docker)*
    *   **Port :** `5432`
    *   **Maintenance database :** `dsr_database`
    *   **Username :** `dsr_admin`

3.  **En cas d'échec de connexion depuis pgAdmin :**
    Vérifier que `dsr-pgadmin` et `dsr-postgres` sont bien attachés au même réseau Docker (`dsr_shared_network`) :
    ```bash
    sudo docker network inspect dsr_shared_network --format '{{range .Containers}}{{.Name}} {{end}}'
    ```

### 💥 Runbook 3 : Saturation Mémoire & `OOM Killer` (*Out Of Memory*)

#### 🚨 Symptômes
*   Un conteneur s'arrête brutalement avec le **Code de sortie `137` (`Exited (137)`)**.
*   Le VPS devient très lent ou ne répond plus en SSH (risque accru lors de l'exécution de traitements lourds du Data Lakehouse avec PySpark, DuckDB et Redpanda).
*   Le noyau Linux (*OOM Killer*) a sacrifié le processus le plus gourmand en RAM pour éviter un crash complet du serveur.

#### 🔍 Diagnostic sur le VPS
```bash
# 1. Vérifier si un conteneur précis a été tué par l'OOM Killer (renvoie "true" ou "false")
sudo docker inspect dsr-api-prod --format='{{.State.OOMKilled}}'

# 2. Consulter les journaux du noyau Linux pour identifier le processus sacrifié
sudo dmesg -T | grep -i -E "killed process|out of memory"

# 3. Surveiller la consommation RAM/CPU en temps réel de chaque conteneur
sudo docker stats --no-stream
```

#### 🔧 Remédiation & Prévention
1.  **Vérifier et activer un fichier d'échange (*Swap*) de 4 Go sur le disque NVMe du VPS** (filet de sécurité en cas de pic de charge ponctuel) :
    ```bash
    # Vérifier si un Swap existe déjà
    swapon --show

    # Créer et activer un Swap de 4 Go si absent
    sudo fallocate -l 4G /swapfile
    sudo chmod 600 /swapfile
    sudo mkswap /swapfile
    sudo swapon /swapfile

    # Rendre le Swap permanent au redémarrage dans /etc/fstab
    echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
    ```
2.  **Plafonner la RAM des services lourds** dans les `docker-compose.yml` (en particulier pour le Data Lakehouse) via la directive `deploy.resources.limits.memory` afin qu'un job Data ne puisse jamais faire tomber PostgreSQL ou HashiCorp Vault.

### 🔺 Runbook 4 : Erreurs Prisma & Synchronisation Base de Données

| Code / Erreur | Cause Probable | Solution Immédiate |
| :--- | :--- | :--- |
| **`P1001: Can't reach database server`** | En local : le conteneur `dsr-postgres` est éteint ou le Tunnel SSH (Runbook 2) est fermé. En Prod : `DATABASE_URL` dans Vault pointe vers `localhost` au lieu de `dsr-postgres`. | Vérifier `docker ps`, rouvrir le tunnel SSH, ou vérifier la valeur `DATABASE_URL` dans Vault (`@dsr-postgres:5432`). |
| **`P2021: The table ... does not exist`** | Le schéma Prisma a évolué dans le code, mais n'a pas encore été poussé sur la base de production. | Ouvrir le Tunnel SSH (Runbook 2), basculer temporairement `DATABASE_URL` vers la prod et lancer `npx prisma db push`. |
| **`@prisma/client did not initialize yet`** | Le client Prisma n'a pas été généré avant la compilation ou les tests (`npm run build` / `vitest`). | Lancer `npx prisma generate` (et vérifier que cette étape précède le lint/test dans `Dockerfile` et `deploy.yml`). |
| **Erreur de droits / Seed en doublon** | Tentative de relancer `npx prisma db seed` sur une base déjà peuplée sans `upsert`. | Utiliser systématiquement `prisma.user.upsert(...)` dans `prisma/seed.ts` pour rendre le seed **idempotent**. |

> [!CAUTION]
> **Règle d'or post-intervention Prisma :** Après avoir poussé un schéma en production via Tunnel SSH, **toujours remettre immédiatement `DATABASE_URL` sur l'environnement local** dans le fichier `.env` de son PC pour éviter toute manipulation accidentelle sur la base de production !

### 🌐 Runbook 5 : Incidents Web, Reverse Proxy & CI/CD (Retours d'Expérience)

Cette section capitalise sur les vrais incidents rencontrés et résolus lors de la mise en production du projet :

1.  **Le Frontend Angular appelle `http://localhost:3000` en production (`ERR_CONNECTION_REFUSED`) :**
    *   *Diagnostic :* La console du navigateur affiche `POST http://localhost:3000/api/v1/auth/login net::ERR_CONNECTION_REFUSED`.
    *   *Cause :* Angular n'a pas remplacé `environment.ts` par `environment.prod.ts` lors du build Docker.
    *   *Solution :* Vérifier dans `angular.json` (`configurations > production`) la présence explicite du bloc `fileReplacements`, ainsi que `"src/assets"` dans le tableau `assets`.
2.  **La barre latérale Docsify disparaît (*Chargement de la documentation...*) lors d'un clic sur un sous-dossier :**
    *   *Diagnostic :* L'accueil fonctionne, mais cliquer sur `/#/docs/architecture/...` remplace le menu latéral par la page d'accueil.
    *   *Cause :* La règle Nginx `try_files $uri $uri/ /index.html;` (conçue pour les SPA Angular) renvoie `index.html` au lieu d'une erreur `404` lorsque Docsify cherche un `_sidebar.md` local dans le sous-dossier.
    *   *Solution :* Dans le `Dockerfile` de `data-skills-radar-docs`, utiliser impérativement **`try_files $uri $uri/ =404;`**.
3.  **Erreur Nginx `502 Bad Gateway` :**
    *   *Diagnostic :* Nginx répond bien en HTTPS, mais le conteneur cible derrière `proxy_pass` est injoignable.
    *   *Solution :* Vérifier que le conteneur tourne (`sudo docker ps`), que le port écouté correspond à la matrice des ports (`3000` API Prod, `3001` API Staging, `4200` App Prod, `4201` App Staging, `4300` Docs : `sudo ss -tulpn | grep LISTEN`), et consulter `sudo docker logs <conteneur>` (souvent lié au Runbook 1 : Vault scellé).
4.  **Échec du job `deploy` GitHub Actions (`ssh.ParsePrivateKey: ssh: no key found`) :**
    *   *Diagnostic :* L'étape `appleboy/ssh-action` échoue immédiatement au handshake SSH.
    *   *Cause :* Le secret GitHub `VPS_SSH_KEY` du dépôt concerné est vide, mal orthographié, ou sa copie a tronqué les en-têtes `-----BEGIN OPENSSH PRIVATE KEY-----` / `-----END OPENSSH PRIVATE KEY-----`.
    *   *Solution :* Recoller la clé privée complète dans *Settings > Secrets and variables > Actions > Repository secrets > `VPS_SSH_KEY`*, puis cliquer sur *Re-run failed jobs*.

## ⚙️ 6.3. Maintien en Conditions Opérationnelles (MCO)

> **Contexte :** Déployer une architecture en production n'est que la première étape. Le **Maintien en Conditions Opérationnelles (MCO)** consiste à garantir dans la durée la disponibilité, la sécurité et la propreté du disque NVMe de mon VPS OVH sans intervention manuelle répétitive.

### 🔒 1. Renouvellement Automatique des Certificats SSL (Certbot)

Les certificats Let's Encrypt ont une durée de validité volontairement courte de **90 jours**. Un timer `systemd` vérifie automatiquement deux fois par jour si un certificat arrive à moins de 30 jours de son expiration et le renouvelle sans coupure.

#### A. Vérifier l'état du timer et des certificats actifs sur le VPS
```bash
sudo systemctl status certbot.timer --no-pager
sudo certbot certificates
```

**Sortie validée sur le VPS :**

### 🔄 2. Rotation des Secrets HashiCorp Vault (Zéro-Trust)

Le moteur **KV-v2** de HashiCorp Vault conserve automatiquement l'historique des versions de chaque secret, permettant une rotation réversible à tout instant.

#### A. Rotation d'un secret applicatif (ex: `JWT_SECRET` ou clés S3 OVH)
> [!TIP]
> **Bon réflexe KV-v2 (`patch` vs `put`) :** La commande `vault kv put` écrase toutes les clés du chemin si on ne les redonne pas toutes. Pour ne modifier qu'une seule clé sans effacer les autres (`DATABASE_URL`, `S3_ENDPOINT`, etc.), j'utilise toujours **`vault kv patch`** !

```bash
# 1. Connexion administrateur dans Vault
sudo docker exec -it dsr-vault vault login

# 2. Mise à jour ciblée du JWT_SECRET en production (crée automatiquement la version N+1)
sudo docker exec -it dsr-vault vault kv patch secret/dataskillsradar/production/backend \
  JWT_SECRET="<NOUVELLE_CLE_JWT_GENEREE>"

# 3. Vérifier l'historique des versions (rollback possible avec : vault kv rollback -version=<N> ...)
sudo docker exec -it dsr-vault vault kv metadata get secret/dataskillsradar/production/backend

# 4. Redémarrer l'API de production pour qu'elle charge le nouveau secret en RAM
sudo docker restart dsr-api-prod
```

#### B. Rotation trimestrielle du `SECRET_ID` AppRole (Sans coupure de service)
```bash
# 1. Générer un nouveau Secret ID pour le rôle de l'API
sudo docker exec -it dsr-vault vault write -f auth/approle/role/dsr-api-role/secret-id

# 2. Mettre à jour VAULT_SECRET_ID dans GitHub Secrets et relancer le job deploy
# 3. Révoquer l'ancien secret_id_accessor une fois l'API redémarrée avec succès :
sudo docker exec -it dsr-vault vault list auth/approle/role/dsr-api-role/secret-id
sudo docker exec -it dsr-vault vault write auth/approle/role/dsr-api-role/secret-id-accessor/destroy \
  secret_id_accessor="<ANCIEN_ACCESSOR>"
```

### 💾 3. Sauvegarde Automatique (Backup) & Restauration PostgreSQL (PRA)

Un volume Docker (`postgres_data`) protège contre le redémarrage d'un conteneur, mais ne protège pas contre une erreur humaine (`DROP TABLE`, mauvaise migration Prisma). J'ai mis en place un **dump SQL quotidien à chaud compressé en Gzip avec rétention glissante de 7 jours**.

#### A. Script de sauvegarde (`/usr/local/bin/backup-dsr-db.sh`)
```bash
#!/bin/bash
set -euo pipefail

BACKUP_DIR="/var/backups/dsr-postgres"
DATE=$(date +"%Y-%m-%d_%H-%M-%S")
FILENAME="${BACKUP_DIR}/dsr_database_${DATE}.sql.gz"

# 1. Création du répertoire sécurisé (droits root stricts 700)
mkdir -p "${BACKUP_DIR}"
chmod 700 "${BACKUP_DIR}"

# 2. Dump à chaud depuis le conteneur PostgreSQL et compression Gzip
docker exec dsr-postgres pg_dump -U dsr_admin -d dsr_database | gzip > "${FILENAME}"

# 3. Nettoyage automatique : suppression des backups de plus de 7 jours
find "${BACKUP_DIR}" -type f -name "*.sql.gz" -mtime +7 -delete

echo "[$(date)] Backup réussi : ${FILENAME}" >> /var/log/dsr-backup.log
```

**Activation et test sur le VPS :**
```bash
sudo chmod +x /usr/local/bin/backup-dsr-db.sh
sudo /usr/local/bin/backup-dsr-db.sh
sudo ls -lh /var/backups/dsr-postgres/
# Résultat : -rw-r--r-- 1 root root 1.8K Nov 19 10:33 dsr_database_2026-11-19_10-33-58.sql.gz
```

#### B. Planification quotidienne via Cron (`sudo crontab -e`)
Exécution automatique chaque nuit à **03h00** :
```cron
0 3 * * * /usr/local/bin/backup-dsr-db.sh
```

#### C. Procédure de Restauration (PRA — Plan de Reprise d'Activité)
En cas d'incident grave nécessitant de restaurer la base de production à partir d'une archive `.sql.gz` :
```bash
gunzip -c /var/backups/dsr-postgres/<FICHIER_BACKUP.sql.gz> | sudo docker exec -i dsr-postgres psql -U dsr_admin -d dsr_database
```

### 🧹 4. Hygiène Docker & Sécurité Système (*Patch Management*)

#### A. Nettoyage automatique des anciennes images Docker (`sudo crontab -e`)
À chaque déploiement CI/CD, de nouvelles images sont téléchargées depuis `ghcr.io`. Pour éviter que les anciennes couches (*dangling images*) ne saturent les 100 Go NVMe du VPS, une seconde tâche Cron purge chaque **dimanche à 04h00** les images inutilisées depuis plus de 7 jours (`168h`) :

```cron
# Purge hebdomadaire des vieilles images Docker (> 168h) - Volumes préservés !
0 4 * * 0 /usr/bin/docker image prune -a -f --filter "until=168h" >> /var/log/dsr-docker-prune.log 2>&1
```

> [!CAUTION]
> **Règle absolue :** Ne jamais utiliser l'option `--volumes` dans une tâche automatique `docker system prune`, sous peine de détruire définitivement la base PostgreSQL (`postgres_data`) ou le coffre chiffré de Vault (`vault_data`) si un conteneur est momentanément arrêté !

#### B. Mises à jour de sécurité Ubuntu automatiques (`unattended-upgrades`)
```bash
sudo apt install unattended-upgrades -y
sudo dpkg-reconfigure -plow unattended-upgrades
```
*(Note : Je laisse volontairement le redémarrage automatique désactivé dans `/etc/apt/apt.conf.d/50unattended-upgrades` afin que le VPS ne redémarre jamais à mon insu — ce qui scellerait HashiCorp Vault ! Si un redémarrage noyau est requis, je le planifie manuellement puis j'exécute immédiatement le **Runbook 1 : Unseal Vault**).*
