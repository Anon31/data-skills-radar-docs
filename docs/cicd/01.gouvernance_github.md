# 🚦 Gouvernance GitHub, Runners & Automatisation CI/CD

Ce chapitre détaille la gouvernance que j'applique sur les 4 dépôts GitHub de l'écosystème **Data Skills Radar** (`app`, `api`, `lakehouse`, `docs`), ainsi que ma stratégie de maintien en condition opérationnelle des runners GitHub Actions face aux dépréciations de runtimes (Node.js 24 et Ubuntu LTS).

---

## 🔒 1. Standardisation des Runners (`ubuntu-24.04` vs `ubuntu-latest`)

À compter d'octobre/novembre 2026, GitHub migre progressivement le label flottant `ubuntu-latest` d'Ubuntu 24.04 vers **Ubuntu 26.04** ([GitHub Runner Images #14748](https://github.com/actions/runner-images/issues/14748)).

Pour éviter deux écueils majeurs :
1. Les avertissements de migration dans mes logs CI/CD (`The ubuntu-latest label will migrate to Ubuntu 26 beginning October 19, 2026`).
2. Les ruptures silencieuses de dépendances système (changements d'outils préinstallés, librairies C/C++ ou versions Docker Buildx lors du basculement automatique du runner).

> [!IMPORTANT]
> **Décision d'Architecture CI/CD :** J'épingle explicitement tous mes jobs GitHub Actions sur **`runs-on: ubuntu-24.04`** (Ubuntu 24.04 LTS Noble Numbat) dans l'ensemble des 4 dépôts. Cela me garantit des builds 100 % déterministes et reproductibles jusqu'à ce que je décide volontairement de basculer vers `ubuntu-26.04`.

---

## ⚡ 2. Migration Intégrale des Actions vers le Runtime Node.js 24

Suite à la dépréciation officielle de **Node.js 20** sur les runners GitHub Actions ([GitHub Changelog — Deprecation of Node 20](https://github.blog/changelog/2025-09-19-deprecation-of-node-20-on-github-actions-runners/)), toute action JavaScript déclarant encore `runs.using: 'node20'` dans son manifeste déclenche un avertissement de dépréciation (`Node.js 20 is deprecated. The following actions target Node.js 20 but are being forced to run on Node.js 24`).

J'ai donc audité et mis à niveau l'intégralité des actions utilisées dans mes workflows vers leurs versions majeures ciblant nativement **Node.js 24** (`node24`) :

| Action GitHub | Ancienne Version (`node20`) | Version Standardisée (`node24`) | Dépôts Concernés | Rôle Technique |
| :--- | :---: | :---: | :--- | :--- |
| **`actions/checkout`** | `@v4` | **`@v6`** | Tous (`app`, `api`, `docs`) | Récupération du code source et isolation sécurisée des identifiants Git dans `$RUNNER_TEMP`. |
| **`actions/setup-node`** | `@v4` | **`@v6`** | `app`, `api` | Provisionnement de l'environnement Node.js `24` avec gestion du cache `npm`. |
| **`actions/configure-pages`** | `@v4` | **`@v6`** | `docs` | Configuration des métadonnées d'hébergement GitHub Pages pour Docsify. |
| **`actions/upload-pages-artifact`** | `@v3` | **`@v5`** | `docs` | Empaquetage de l'archive statique (s'appuie en interne sur `actions/upload-artifact@v7` en Node 24). |
| **`actions/deploy-pages`** | `@v4` | **`@v5`** | `docs` | Déploiement atomique de l'artefact Docsify sur GitHub Pages. |
| **`docker/login-action`** | `@v3` | **`@v4`** | `app`, `api` | Authentification auprès du registre d'images GitHub (`ghcr.io`). |
| **`docker/build-push-action`** | `@v6` | **`@v7`** | `app`, `api` | Construction multi-étapes du `Dockerfile` et publication sur `ghcr.io`. |
| **`release-drafter/release-drafter`** | `@v5` | **`@v7`** | Tous (`app`, `api`, `lakehouse`, `docs`) | Génération automatique des notes de version (Changelog SemVer) à chaque push sur `develop` et `master`. |

## 🏷️ 3. Automatisation du Changelog avec Release Drafter

Dans chacun de mes 4 dépôts, j'ai configuré **Release Drafter** via deux fichiers complémentaires :
1. **Le workflow d'exécution** (`.github/workflows/release-drafter.yml`) déclenché sur les branches `master` et `develop`.
2. **La configuration déclarative** (`.github/release-drafter.yml`) qui réalise trois opérations automatiques :
   - **Autolabeling des Pull Requests** : Analyse le préfixe Conventional Commits (`feat:`, `fix:`, `docs:`, `style:`, `refactor:`, `test:`, `chore:`, `ci:`/`cicd:`) pour apposer automatiquement le label GitHub correspondant.
   - **Catégorisation visuelle** : Regroupe les PR fusionnées par thématiques (`🚀 Nouvelles Fonctionnalités`, `🐛 Corrections de Bugs`, `📚 Documentation`, `🏭 CI/CD & DevOps`, etc.).
   - **Calcul SemVer (`$RESOLVED_VERSION`)** : Incrémente automatiquement la version `major`, `minor` (pour `feature`) ou `patch` (pour `fix`, `docs`, `cicd`, `chore`, etc.).
