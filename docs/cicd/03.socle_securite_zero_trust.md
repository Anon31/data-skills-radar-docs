# 🔐 3. Socle de Sécurité & Zéro-Trust (HashiCorp Vault, AppRole, Tunnel SSH & DX)

> **Objectif de ce chapitre :** Documenter la mise en œuvre de ma stratégie **Shift-Left Security & Zéro-Trust** : le déploiement de **HashiCorp Vault 1.15** en mode *Hardened* (*Shamir's Secret Sharing*), l'authentification Machine-to-Machine par **AppRole (`ROLE_ID` / `SECRET_ID`)**, le confinement de **PostgreSQL 16** et **pgAdmin** derrière un **Tunnel SSH**, ainsi que l'automatisation de mon environnement de développement local via le script **`init-vault.sh`**.

---

## 🗝️ 2.1. Déploiement de HashiCorp Vault en Mode Hardened (Zéro-Trust)

> **Contexte :** Dans une architecture *Shift-Left Security*, les mots de passe de base de données, les clés API (France Travail, INSEE), les accès S3 OVH et les clés de signature JWT ne doivent jamais se trouver en clair dans le code source (GitHub) ni dans des fichiers `.env` persistants sur le disque du serveur. J'ai déployé **HashiCorp Vault** comme unique source de vérité cryptographique de mon infrastructure.

### 1. La Stratégie de Scellement (*Shamir's Secret Sharing*)

Par défaut, Vault démarre dans un état **scellé (`Sealed: true`)**. Il sait où sont stockées les données chiffrées sur le disque NVMe du VPS, mais il ne possède pas la clé maître en mémoire vive pour les déchiffrer. Vault utilise l'algorithme cryptographique de **Shamir** pour diviser cette clé maître en plusieurs fragments (**5 clés générées, dont un quorum de 3 est requis** pour reconstruire la clé maître en RAM).

*   **Pourquoi conserver ce mode manuel en production ?** C'est la garantie absolue de sécurité Zéro-Trust. Si le VPS est compromis physiquement ou redémarré à mon insu, Vault se verrouille automatiquement : tous les secrets deviennent mathématiquement illisibles sur le disque dur jusqu'à ce que je fournisse manuellement 3 fragments valides.

### 2. Déploiement Docker sur le VPS (Opérations de Bootstrapping)

Pour amorcer Vault sur le VPS au sein de l'écosystème `data-skills-radar-api`, j'ai créé l'arborescence `~/data-skills-radar-api/vault/config/` et son fichier de configuration :

#### A. Fichier `vault/config/vault.json`
Configure le backend de stockage persistant sur disque (`file`) et désactive le TLS interne (car le conteneur Vault n'est jamais exposé sur Internet et n'écoute qu'en local) :

```json
{
  "storage": {
    "file": {
      "path": "/vault/file"
    }
  },
  "listener": {
    "tcp": {
      "address": "0.0.0.0:8200",
      "tls_disable": 1
    }
  },
  "ui": true,
  "disable_mlock": true
}
```

#### B. Fichier `docker-compose.yml` (Socle Initial Vault)
> [!WARNING]
> **Note technique sur l'entrypoint Vault :** L'image officielle `hashicorp/vault` charge automatiquement tous les fichiers présents dans `/vault/config`. Il est crucial d'utiliser simplement `command: server` (et non `server -config=...`), sous peine de charger la configuration deux fois et de provoquer un crash au démarrage (`bind: address already in use`).

```yaml
services:
  dsr-vault:
    image: hashicorp/vault:1.15
    container_name: dsr-vault
    environment:
      VAULT_ADDR: "http://127.0.0.1:8200"
      VAULT_API_ADDR: "http://127.0.0.1:8200"
    ports:
      - "127.0.0.1:8200:8200" # ⚠️ Accessible uniquement depuis localhost (VPS)
    volumes:
      - vault_data:/vault/file
      - ./vault/config:/vault/config
    cap_add:
      - IPC_LOCK # Empêche la mémoire RAM d'être écrite sur le fichier d'échange (Swap)
    command: server

volumes:
  vault_data:
```

#### C. Séquence de commandes d'installation exécutées sur le VPS
```bash
# 1. Création de l'arborescence des dossiers
mkdir -p ~/data-skills-radar-api/vault/config
cd ~/data-skills-radar-api

# 2. Création des fichiers vault/config/vault.json et docker-compose.yml
nano vault/config/vault.json
nano docker-compose.yml

# 3. Démarrage du conteneur en arrière-plan
sudo docker compose up -d

# 4. Initialisation cryptographique du coffre (Génération des clés maîtresses)
sudo docker exec -it dsr-vault vault operator init
```

> [!NOTE]
> **Note de dépannage :** En cas d'erreur lors de l'initialisation nécessitant une remise à zéro complète du coffre, il faut détruire le volume Docker protégé avec `sudo docker compose down -v`, puis relancer `up -d` et `vault operator init`.

### 4. Configuration du Moteur de Secrets (`KV-v2`) et de la Politique de Moindre Privilège

Une fois le coffre déverrouillé en mémoire vive, j'ai activé le moteur **Key-Value v2** (qui supporte le versioning des secrets) et créé une politique d'accès en lecture seule :

```bash
# 1. Authentification avec mon Token Administrateur (Root)
sudo docker exec -it dsr-vault vault login hvs.S2bq2N************CSgRC7

# 2. Activation du moteur Key-Value (version 2) sur le chemin "secret/"
sudo docker exec -it dsr-vault vault secrets enable -path=secret kv-v2

# 3. Création de la Policy de lecture seule "dsr-read-policy"
sudo docker exec -i dsr-vault vault policy write dsr-read-policy - <<EOF
path "secret/data/dataskillsradar/*" {
  capabilities = ["read"]
}
EOF
```
*(Note technique : Dans le moteur `KV-v2`, Vault intercale automatiquement le préfixe `/data/` derrière le nom du chemin principal lors de la définition des règles d'accès).*

### 5. Injection des Secrets S3 OVH & JWT

> [!TIP]
> **Pourquoi préfixer mes clés par `AWS_` alors que je suis chez OVHcloud ?**  
> L'Object Storage d'OVH utilise le protocole standard mondial **S3** (initialement créé par Amazon Web Services). La quasi-totalité des librairies et moteurs analytiques (**DuckDB**, **PySpark**, **Boto3**, **AWS SDK**) sont programmés par défaut pour chercher automatiquement dans la mémoire du serveur les variables nommées `AWS_ACCESS_KEY_ID` et `AWS_SECRET_ACCESS_KEY`. Conserver cette convention me permet une compatibilité **Zero-Config** avec tous mes outils Big Data, tout en redirigeant les flux vers le datacenter français d'OVH (Gravelines) grâce aux variables `S3_ENDPOINT="https://s3.gra.io.cloud.ovh.net"` et `S3_REGION="gra"`.

## 🤖 2.2. Authentification Machine-to-Machine : Configuration de l'AppRole (`RoleID` / `SecretID`)

> **Contexte :** Une application backend (comme mon API NestJS) ne doit jamais utiliser le Token Root administrateur pour lire ses secrets. J'ai mis en place le mécanisme **AppRole**, standard industriel pour l'authentification *Machine-to-Machine* sans intervention humaine.

### 1. Fonctionnement du couple `ROLE_ID` / `SECRET_ID`
1.  **Le `ROLE_ID` :** L'identifiant public du rôle (comparable à un *Username* applicatif fixe).
2.  **Le `SECRET_ID` :** Le mot de passe cryptographique associé au rôle (secret, renouvelable et révocable).

Au démarrage, mon API NestJS se présente à Vault avec son `ROLE_ID` et son `SECRET_ID`. Vault vérifie le couple et lui délivre un jeton client temporaire (`token_ttl=1h`, `token_max_ttl=4h`) limité à la politique `dsr-read-policy`.

### 2. Commandes Exécutées sur le VPS
```bash
# 1. Activation du moteur d'authentification AppRole
sudo docker exec -it dsr-vault vault auth enable approle

# 2. Création de l'AppRole "dsr-api-role" lié à la politique "dsr-read-policy"
sudo docker exec -it dsr-vault vault write auth/approle/role/dsr-api-role \
    token_policies="dsr-read-policy" \
    token_ttl=1h \
    token_max_ttl=4h

# 3. Récupération du Role ID (Fixe)
sudo docker exec -it dsr-vault vault read auth/approle/role/dsr-api-role/role-id

# 4. Génération du Secret ID (Sensible)
sudo docker exec -it dsr-vault vault write -f auth/approle/role/dsr-api-role/secret-id
```

**Valeurs générées (injectées ensuite dans les Secrets GitHub Actions au Chapitre 3) :**
*   **Role ID :** `58c8f63b-****-****-****-b5285ed38f10`
*   **Secret ID :** `f334c1bc-****-****-****-3770e26446cb`

## 🐘 2.3. Déploiement de PostgreSQL 16 & Sécurisation pgAdmin par Tunnel SSH

> **Enjeu Zéro-Trust :** Une base de données de production ne doit jamais être exposée publiquement sur Internet. J'ai verrouillé l'écoute de **PostgreSQL 16** (`5432`) et de **pgAdmin 4** (`5050`) sur la boucle locale `127.0.0.1` du VPS et j'utilise un **Tunnel SSH** pour les administrer et pousser mes migrations Prisma depuis mon poste de développement.

### 1. Orchestration `docker-compose.prod.yml` (Socle Base de Données & Vault)

```yaml
services:
  # 1. Le Coffre-Fort (Initialisé et déverrouillé)
  dsr-vault:
    image: hashicorp/vault:1.15
    container_name: dsr-vault
    environment:
      VAULT_ADDR: "http://127.0.0.1:8200"
      VAULT_API_ADDR: "http://127.0.0.1:8200"
    ports:
      - "127.0.0.1:8200:8200"
    volumes:
      - vault_data:/vault/file
      - ./vault/config:/vault/config
    cap_add:
      - IPC_LOCK
    command: server

  # 2. La Base de Données Relationnelle de Production (OLTP)
  dsr-postgres:
    image: postgres:16-alpine
    container_name: dsr-postgres
    restart: always
    environment:
      POSTGRES_USER: "dsr_admin"
      POSTGRES_PASSWORD: "dsr_master_password_2026"
      POSTGRES_DB: "dsr_database"
    ports:
      - "127.0.0.1:5432:5432" # 🔒 Protégé : local (VPS) uniquement
    volumes:
      - postgres_data:/var/lib/postgresql/data

  # 3. L'Interface d'Administration DB
  dsr-pgadmin:
    image: dpage/pgadmin4
    container_name: dsr-pgadmin
    restart: always
    environment:
      PGADMIN_DEFAULT_EMAIL: "admin@dataskills.dev"
      PGADMIN_DEFAULT_PASSWORD: "pgadmin_secure_2026"
    ports:
      - "127.0.0.1:5050:80" # 🔒 Protégé : Tunnel SSH requis
    depends_on:
      - dsr-postgres

volumes:
  vault_data:
  postgres_data:
```

### 2. La Magie du Tunnel SSH (Administration & Déploiement du Schéma Prisma)

Depuis le terminal de mon PC local (Windows PowerShell / WSL), j'ouvre un tunnel chiffré qui déporte les ports `5050` et `5432` du VPS sur mon `localhost` :

```bash
ssh -L 5050:localhost:5050 -L 5432:localhost:5432 ubuntu@51.210.101.236
```

#### A. Visualisation Web via pgAdmin (`http://localhost:5050`)
Tant que la fenêtre SSH est ouverte, pgAdmin est accessible sur `http://localhost:5050` et se connecte au serveur PostgreSQL interne via le nom DNS Docker **`dsr-postgres`** (port `5432`, utilisateur `dsr_admin`, base `dsr_database`).

#### B. Mode Opératoire : Pousser le Schéma Prisma et les Seeds en Production
Grâce au tunnel SSH actif sur le port `5432`, j'ai pu initialiser la base de données de production directement depuis mon IDE local sans jamais exposer PostgreSQL sur Internet :
1.  Ouverture du Tunnel SSH en arrière-plan.
2.  Bascule temporaire de `DATABASE_URL` dans mon fichier `.env` local vers l'URL de production (`postgresql://dsr_admin:...@localhost:5432/dsr_database?schema=public`).
3.  Exécution de la synchronisation du schéma et du peuplement initial (*Seeding*) :

## 🛠️ 2.4. Expérience Développeur (DX) & Script `init-vault.sh` en Local

> **Contexte :** Sur mon PC de développement local, je détruis et recrée régulièrement mes conteneurs (`docker compose down/up`). Comme le conteneur Vault local tourne en mode `Dev` (en mémoire vive), il redémarre vide. Pour éviter que mon API NestJS ne crashe au démarrage et ne jamais avoir à retaper les commandes de configuration Vault à la main, j'ai créé un script d'amorçage automatique **`init-vault.sh`**.

### 1. Fonctionnement du Script `init-vault.sh`
1.  Vérifie que le conteneur `dsr-vault` local tourne bien.
2.  S'authentifie automatiquement avec le Token de développement (`dsr_dev_vault_token`).
3.  Active le moteur `kv-v2` et injecte les secrets de développement dans `secret/dataskillsradar/development/backend`.
4.  Crée la politique `dsr-read-policy` et configure l'AppRole `dsr-api-role` en **forçant des identifiants statiques (`role_id="local-dev-role-id"` et `secret_id="local-dev-secret-id"`)** afin que mon fichier `.env` local n'ait jamais besoin d'être modifié !

### 2. Code Complet du Script (`init-vault.sh`)

```bash
#!/bin/bash

# ==============================================================================
# Script d'amorçage local pour HashiCorp Vault (Data Skills Radar)
# ==============================================================================

VAULT_CONTAINER="dsr-vault"
DEV_TOKEN="dsr_dev_vault_token"
VAULT_URL="http://127.0.0.1:8200"

echo "⏳ Vérification de l'état de Vault..."

# Vérification que le conteneur tourne bien avant de continuer
if ! docker ps | grep -q $VAULT_CONTAINER; then
  echo "❌ Erreur : Le conteneur $VAULT_CONTAINER ne tourne pas !"
  echo "👉 Lance d'abord : docker compose up -d"
  exit 1
fi

sleep 3

# 1. Connexion en Root (Mode Dev)
echo "🔑 Authentification..."
docker exec -e VAULT_ADDR=$VAULT_URL -i $VAULT_CONTAINER vault login $DEV_TOKEN

# 2. Activation du moteur de secrets (Key-Value v2)
echo "📂 Activation du moteur KV-v2..."
docker exec -e VAULT_ADDR=$VAULT_URL -i $VAULT_CONTAINER vault secrets enable -path=secret kv-v2 2>/dev/null || true

# 3. Injection des secrets locaux (Variables de dev — connectées à OVH Object Storage S3 Gravelines)
# NOTE: Le chemin correspond exactement à ce que NestJS demande (dataskillsradar/development/backend)
echo "💉 Injection des secrets de développement..."
docker exec -e VAULT_ADDR=$VAULT_URL -i $VAULT_CONTAINER vault kv put secret/dataskillsradar/development/backend \
  JWT_SECRET="une_cle_secrete_tres_longue_et_complexe_pour_le_dev_2026" \
  AWS_ACCESS_KEY_ID="701077cb****************d0b80411" \
  AWS_SECRET_ACCESS_KEY="7d6151be****************e40662d" \
  S3_ENDPOINT="https://s3.gra.io.cloud.ovh.net" \
  S3_REGION="gra" \
  S3_BUCKET_BRONZE="dsr-bronze-s3" \
  S3_BUCKET_SILVER="dsr-silver-s3" \
  S3_BUCKET_GOLD="dsr-gold-s3"

# 4. Configuration de la Policy
echo "📜 Création de la policy de lecture..."
docker exec -e VAULT_ADDR=$VAULT_URL -i $VAULT_CONTAINER vault policy write dsr-read-policy - <<EOF
path "secret/data/dataskillsradar/*" {
  capabilities = ["read"]
}
EOF

# 5. Activation et configuration de l'AppRole (Machine-to-Machine)
echo "🤖 Configuration de l'AppRole..."
docker exec -e VAULT_ADDR=$VAULT_URL -i $VAULT_CONTAINER vault auth enable approle 2>/dev/null || true

docker exec -e VAULT_ADDR=$VAULT_URL -i $VAULT_CONTAINER vault write auth/approle/role/dsr-api-role \
  token_policies="dsr-read-policy" \
  token_ttl=1h \
  token_max_ttl=4h

# Forçage d'un Role ID et d'un Secret ID statiques pour le confort de développement local
docker exec -e VAULT_ADDR=$VAULT_URL -i $VAULT_CONTAINER vault write auth/approle/role/dsr-api-role/role-id \
  role_id="local-dev-role-id"

docker exec -e VAULT_ADDR=$VAULT_URL -i $VAULT_CONTAINER vault write auth/approle/role/dsr-api-role/custom-secret-id \
  secret_id="local-dev-secret-id"

echo "✅ Vault local est prêt et configuré !"
echo "ROLE_ID   = local-dev-role-id"
echo "SECRET_ID = local-dev-secret-id"
```
