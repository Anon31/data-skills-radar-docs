### 2. Le Stockage : Le Data Lakehouse (OVH Object Storage S3)

Pour implémenter mon architecture **Medallion (`Bronze`, `Silver`, `Gold`)**, le disque dur local du VPS n'est ni adapté, ni suffisant à long terme. J'applique le principe fondamental du Cloud moderne : **séparer le calcul (*Compute*) du stockage (*Storage*)**.

#### Mon Choix : OVH Object Storage — One Zone (Compatible S3)

Lors du choix de mon Object Storage, j'ai procédé à une analyse **FinOps** (optimisation des coûts) en comparant les offres d'OVHcloud :
*   **Multi Zone (`3-AZ / Paris`) à `~0,0139941 € HT/Gio/mois` :** Les données sont répliquées sur 3 datacenters distincts (avec des paliers dégressifs au-delà de 50 Tio). Idéal pour une production bancaire critique, mais sur-dimensionné pour un démonstrateur de Master.
*   **One Zone (`1-AZ / Gravelines`) à `~0,0070956 € HT/Gio/mois` :** Les données résident sur un seul datacenter (**celui de mon VPS !**). C'est presque **50 % moins cher**, avec un **tarif unique et linéaire (*flat rate*)** dès le premier octet, sans paliers.

> [!IMPORTANT]
> **Décision FinOps :** J'opte pour l'offre **One Zone (`Gravelines - 1-AZ`)**. Pour un projet de fin d'études, la réplication géographique sur 3 datacenters n'est pas nécessaire. De plus, **le trafic Entrant/Sortant (*Ingress/Egress*) interne à Gravelines reste 100 % gratuit**, ce qui est fondamental pour exécuter les requêtes analytiques lourdes de mon Lakehouse (PySpark / DuckDB) sans jamais exploser le budget.

## 🌐 1.2. Gestion de la Zone DNS via Netlify et Plan de Nommage

> **Contexte :** Bien que mon nom de domaine racine (`thomasnoel.dev`) soit enregistré chez OVH, la gestion de ma zone DNS est déléguée à **Netlify**. J'ai configuré cette zone pour que tout le trafic des sous-domaines `*.dataskills.thomasnoel.dev` soit redirigé vers mon serveur VPS OVH.

### 1. Principe de Délégation et Architecture « Single-Host »
Dans mon architecture *Single-Host Docker*, le VPS est l'unique point d'entrée réseau. Par conséquent, j'utilise uniquement des enregistrements DNS de **Type `A` (Address)** faisant correspondre chaque sous-domaine à l'adresse IPv4 publique unique de mon VPS (`51.210.101.236`, avec un `TTL` par défaut de `3600` secondes).

C'est ensuite le **Reverse Proxy (Nginx)** installé physiquement sur mon VPS qui analyse le sous-domaine demandé (*Host Header*) et redirige la requête vers le bon conteneur Docker en interne.

## 🛡️ 1.4. Sécurité Périmétrique et Configuration Hôte (Ubuntu 26.04 LTS)

> **Contexte :** Le serveur OVH (VPS) a été livré avec une installation brute d'**Ubuntu 26.04 LTS**. Avant d'y déployer la moindre application ou base de données, j'ai verrouillé ses accès, sécurisé le réseau avec un pare-feu strict et installé le socle technique (`Docker`, `Nginx`, `Certbot`).

### 1. Première Connexion SSH et Sécurisation Initiale
Connexion initiale depuis mon terminal local :
```bash
ssh ubuntu@51.210.101.236
```
Lors de cette première connexion, la politique de sécurité d'Ubuntu (`PAM`) force l'expiration immédiate du mot de passe temporaire fourni par OVHcloud et impose la saisie d'un nouveau mot de passe fort.

> [!WARNING]
> **Troubleshooting (`Authentication token manipulation error`) :**  
> Si cette erreur apparaît et coupe la connexion lors du premier changement de mot de passe, cela signifie que la saisie du *"Current password"* contenait un espace invisible copié par erreur. Il suffit de relancer `ssh ubuntu@51.210.101.236` et de coller le mot de passe éphémère sans caractères parasites.

### 2. Mise à Jour du Système (*Patch Management*)
Application immédiate des correctifs de sécurité du noyau Linux (`*** System restart required ***`) :
```bash
sudo apt update
sudo apt upgrade -y
sudo reboot
```

### 3. Configuration du Pare-feu UFW (*Zéro-Trust Réseau*)
Par défaut, les ports d'un serveur neuf sont ouverts. J'applique une politique de **liste blanche (*Allowlist*) stricte** via `UFW` (*Uncomplicated Firewall*) :

```bash
# 1. On refuse par défaut toutes les connexions entrantes
sudo ufw default deny incoming

# 2. On autorise le trafic sortant (pour télécharger nos images Docker et appeler les APIs Open Data)
sudo ufw default allow outgoing

# 3. On ouvre UNIQUEMENT les 3 ports standards nécessaires
sudo ufw allow 22/tcp   # SSH (Vital pour l'administration et le déploiement GitHub Actions)
sudo ufw allow 80/tcp   # HTTP (Validation Certbot & redirection HTTPS Nginx)
sudo ufw allow 443/tcp  # HTTPS (Trafic web chiffré)

# 4. Activation et vérification du pare-feu
sudo ufw enable
sudo ufw status
```

**Sortie de validation sur le VPS :**
```text
ubuntu@vps-25bb9af5:~$ sudo ufw status
Status: active

To                         Action      From
--                         ------      ----
22/tcp                     ALLOW       Anywhere
80/tcp                     ALLOW       Anywhere
443/tcp                    ALLOW       Anywhere
22/tcp (v6)                ALLOW       Anywhere (v6)
80/tcp (v6)                ALLOW       Anywhere (v6)
443/tcp (v6)               ALLOW       Anywhere (v6)
```

> [!IMPORTANT]
> Tous les autres ports (`3000`, `3001`, `4200`, `4201`, `4300`, `5050`, `5432`, `8200`, `19092`) sont **délibérément bloqués depuis Internet**. Seul le Reverse Proxy Nginx de l'hôte (port `443`) fait le passe-plat en interne vers les applications web, tandis que `pgAdmin` (`5050`) et `PostgreSQL` (`5432`) ne sont joignables que via un Tunnel SSH.

### 4. Installation du Socle Technique (`Docker Compose V2`, `Nginx`, `Certbot`)
```bash
# Installation de Docker et du plugin Compose V2
sudo apt install docker.io docker-compose-v2 -y

# Activation de Docker au démarrage du serveur
sudo systemctl enable docker
sudo systemctl start docker

# Installation de Nginx (Reverse Proxy bare-metal) et Certbot (SSL Let's Encrypt)
sudo apt install nginx certbot python3-certbot-nginx -y

# Activation de Nginx au démarrage
sudo systemctl enable nginx
sudo systemctl start nginx
```
