# 🏭 Architecture CI/CD - Data Skills Radar

## 1. Philosophie DevOps
L'intégration et le déploiement continus de **Data Skills Radar** s'appuient sur les GitHub Actions. L'objectif est d'automatiser le contrôle qualité (linting, tests), la sémantique des versions (SemVer) et le déploiement conteneurisé sur un VPS cible, tout en isolant strictement les environnements de `staging` et de `production`.

## 2. Workflows Git et Pull Requests

Afin de garantir un historique propre et de générer automatiquement les notes de version, nous appliquons la convention **Conventional Commits**.

### A. PR Title Check (`pr-title-check.yml`)
Bloque la validation de toute Pull Request dont le titre ne respecte pas la syntaxe :
`<type>(<scope optionnel>): <description>`

**Types autorisés :**
- `feat` : Nouvelle fonctionnalité
- `fix` : Correction de bug
- `docs` : Documentation
- `style` : Formatage (CSS, Prettier)
- `refactor` : Restructuration du code sans changement de comportement
- `test` : Ajout/Modification de tests
- `chore` : Tâches de maintenance (dépendances)
- `cicd` / `ci` : Scripts et pipelines

### B. PR Auto Labeler (`pr-labeler.yml`)
Assigne automatiquement une étiquette (label) à la Pull Request en fonction de son titre (ex: `feat(ui): bouton` recevra le label `feature`). Cela alimente directement le générateur de Release.

### C. Release Drafter (`release-drafter.yml`)
À chaque fusion sur les branches `develop` ou `master`, ce script rédige un brouillon de *Release Note* (Changelog) en classant les Pull Requests par catégories (Nouvelles fonctionnalités, Corrections, etc.) et calcule la prochaine version sémantique de l'application (Majeure, Mineure, Patch).

## 3. Pipeline de Déploiement (`deploy.yml`)

Ce workflow se déclenche sur tout `push` ou `pull_request` vers `master` (Production) ou `develop` (Staging). Il utilise **Node.js 24**.

### Étape 1 : Continuous Integration (CI)
1. Installation des dépendances (`npm ci`).
2. Exécution du Linting d'Angular (ESLint).
3. (À venir) Exécution des tests unitaires automatisés.

### Étape 2 : Continuous Delivery (CD - Registre)
1. Connexion au GitHub Container Registry (`ghcr.io`).
2. Construction (Build) de l'image Docker front-end.
3. Poussée (Push) de l'image avec le tag correspondant à la branche (`:staging` ou `:production`).

### Étape 3 : Continuous Deployment (CD - Serveur)
Connexion SSH au VPS via clés sécurisées pour exécuter le redéploiement dynamique.

**Matrice des environnements (Isolation Docker) :**
Le script gère deux environnements sur le même serveur en modifiant dynamiquement les ports exposés et les variables d'environnement (`.env.staging` vs `.env.production`).

| Service | Staging (develop) | Production (master) |
| :--- | :--- | :--- |
| **Nom du projet Docker** | `dsr-staging` | `dsr-production` |
| **Port Front-end** | `4201` | `4202` |

*(Note : L'architecture complète inclura prochainement les ports Backend, Base de données et Vault).*
