# 🚀 4. Usine Logicielle CI/CD & Reverse Proxy (Backend API NestJS)

> **Objectif de ce chapitre :** Documenter la construction de mon usine logicielle CI/CD basée sur **GitHub Actions** et **GitHub Container Registry (`ghcr.io`)** pour mon backend **`data-skills-radar-api`**, la gestion Zéro-Trust des secrets SSH et AppRole, la mutualisation du réseau Docker **`dsr_shared_network`** entre Staging et Production, ainsi que la configuration du Reverse Proxy **Nginx** et des certificats **SSL Let's Encrypt (Certbot)**.

## ⚙️ 3.1. Usine Logicielle (CI/CD) & Gestion des Secrets GitHub

> **Contexte :** Mon infrastructure de production et de staging étant prête sur le VPS et mon environnement local automatisé, j'ai construit une chaîne de déploiement continu garantissant une séparation stricte :
> *   À chaque push/merge sur la branche **`develop`**, GitHub compile l'image Docker `:staging` et déploie automatiquement l'API de **Staging** (Port `3001`) sur `https://api-staging.dataskills.thomasnoel.dev`.
> *   À chaque push/merge sur la branche **`master`**, GitHub compile l'image Docker `:production` et déploie automatiquement l'API de **Production** (Port `3000`) sur `https://api.dataskills.thomasnoel.dev`.

### 1. Configuration de l'Accès SSH Automatisé (GitHub Runners → VPS OVH)

Pour que les runners GitHub Actions puissent se connecter à mon VPS et piloter Docker Compose à ma place sans mot de passe, j'ai généré sur le VPS une paire de clés cryptographiques asymétriques dédiée de type **ED25519** (révocable indépendamment à tout moment) :

```bash
# 1. Génération de la clé ED25519 (sans passphrase pour l'automatisation CI/CD)
ssh-keygen -t ed25519 -C "github-actions-deploy" -f ~/.ssh/github_actions_key -N ""

# 2. Autorisation de la clé publique sur le serveur
cat ~/.ssh/github_actions_key.pub >> ~/.ssh/authorized_keys

# 3. Affichage de la clé privée (à enregistrer dans les Secrets GitHub Actions)
cat ~/.ssh/github_actions_key
```

*   **Empreinte (*Fingerprint*) générée sur mon VPS :** `SHA256:0ZTUtbzXS7VvYHyw2YOcx3xsr6/phRlHOO6OcxoW0Y0`

### 4. Préparation des Fichiers Docker Compose sur le VPS (`Prod` & `Staging`)

Puisque `docker-compose.prod.yml` et `docker-compose.staging.yml` sont ignorés par Git, ils résident directement sur le VPS dans `~/data-skills-radar-api/`.

Pour économiser la mémoire vive (RAM) du VPS, **l'API de Staging (port `3001`) ne recrée ni un second Vault ni un second serveur PostgreSQL** : elle se branche sur le réseau Docker explicite **`dsr_shared_network`** créé par la stack de production pour interroger le même `dsr-vault` et le même `dsr-postgres`.

#### A. Fichier `~/data-skills-radar-api/docker-compose.prod.yml` (Sur le VPS)
```yaml
services:
  dsr-api-prod:
    image: ghcr.io/${IMAGE_NAME}:production
    container_name: dsr-api-prod
    restart: always
    ports:
      - "127.0.0.1:3000:3000"
    env_file:
      - .env.production
    depends_on:
      - dsr-vault
      - dsr-postgres
    networks:
      - dsr_network

  dsr-vault:
    image: hashicorp/vault:1.15
    container_name: dsr-vault
    environment:
      VAULT_ADDR: "http://127.0.0.1:8200"
      VAULT_API_ADDR: "http://127.0.0.1:8200"
    ports:
      - "127.0.0.1:8200:8200"
    volumes:
      - vault_data:/vault/file
      - ./vault/config:/vault/config
    cap_add:
      - IPC_LOCK
    command: server
    networks:
      - dsr_network

  dsr-postgres:
    image: postgres:16-alpine
    container_name: dsr-postgres
    restart: always
    environment:
      POSTGRES_USER: "dsr_admin"
      POSTGRES_PASSWORD: "dsr_master_password_2026"
      POSTGRES_DB: "dsr_database"
    ports:
      - "127.0.0.1:5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data
    networks:
      - dsr_network

  dsr-pgadmin:
    image: dpage/pgadmin4
    container_name: dsr-pgadmin
    restart: always
    environment:
      PGADMIN_DEFAULT_EMAIL: "admin@dataskills.dev"
      PGADMIN_DEFAULT_PASSWORD: "pgadmin_secure_2026"
    ports:
      - "127.0.0.1:5050:80"
    depends_on:
      - dsr-postgres
    networks:
      - dsr_network

volumes:
  vault_data:
  postgres_data:

networks:
  dsr_network:
    name: dsr_shared_network
```

#### B. Fichier `~/data-skills-radar-api/docker-compose.staging.yml` (Sur le VPS)
Ce fichier ultra-léger déploie uniquement le conteneur `dsr-api-staging` sur le port `3001` et le rattache au réseau existant `dsr_shared_network` :

#### C. Alignement des Chemins Vault sur le VPS (`staging` & `production`)
Mon application NestJS interroge dynamiquement le chemin `secret/data/dataskillsradar/<NODE_ENV>/backend` au démarrage. J'ai donc injecté les secrets dédiés aux deux environnements dans le Vault du VPS :

```bash
# 1. Mise à jour de la policy pour autoriser la lecture sur dataskillsradar/*
sudo docker exec -i dsr-vault vault policy write dsr-read-policy - <<EOF
path "secret/data/dataskillsradar/*" {
  capabilities = ["read"]
}
EOF

# 2. Injection des secrets pour l'environnement STAGING (Branche develop)
sudo docker exec -it dsr-vault vault kv put secret/dataskillsradar/staging/backend \
  DATABASE_URL="postgresql://dsr_admin:dsr_master_password_2026@dsr-postgres:5432/dsr_database?schema=public" \
  JWT_SECRET="staging_secret_jwt_master_key_2026" \
  AWS_ACCESS_KEY_ID="701077cb****************d0b80411" \
  AWS_SECRET_ACCESS_KEY="7d6151be****************e40662d" \
  S3_ENDPOINT="https://s3.gra.io.cloud.ovh.net" \
  S3_REGION="gra"

# 3. Injection des secrets pour l'environnement PRODUCTION (Branche master)
sudo docker exec -it dsr-vault vault kv put secret/dataskillsradar/production/backend \
  DATABASE_URL="postgresql://dsr_admin:dsr_master_password_2026@dsr-postgres:5432/dsr_database?schema=public" \
  JWT_SECRET="super_secret_jwt_master_key_2026" \
  AWS_ACCESS_KEY_ID="701077cb****************d0b80411" \
  AWS_SECRET_ACCESS_KEY="7d6151be****************e40662d" \
  S3_ENDPOINT="https://s3.gra.io.cloud.ovh.net" \
  S3_REGION="gra"
```

> [!NOTE]
> **Note d'Architecte (Mutualisation de la Base en POC vs Isolation par Schéma en Entreprise) :**  
> Dans ma configuration actuelle, pointer `staging` et `production` vers le même schéma `?schema=public` de `dsr_database` me permet de retrouver instantanément mes comptes utilisateurs sur les deux environnements sans dupliquer le seeding. En contexte industriel, si l'on souhaite isoler totalement les données de test tout en conservant un unique conteneur PostgreSQL (0 Mo de RAM supplémentaire), il suffit de remplacer `?schema=public` par `?schema=staging` dans la variable `DATABASE_URL` du compartiment Vault `staging/backend`.

### 5. Le Pipeline GitHub Actions Complet (`.github/workflows/deploy.yml`)

Voici le workflow complet de `data-skills-radar-api`. Il vérifie le code (Prisma + ESLint + tests unitaires Vitest), construit et pousse l'image Docker sur `ghcr.io`, puis se connecte en SSH au VPS pour générer le fichier d'amorçage `.env.<TAG>` (contenant uniquement l'adresse de Vault et les identifiants AppRole) et relancer le conteneur correspondant :

```yaml
name: CI/CD Pipeline - Data Skills Radar API

on:
  push:
    branches: [ "master", "develop" ]
  pull_request:
    branches: [ "master", "develop" ]

jobs:
  build-and-push:
    runs-on: ubuntu-24.04
    permissions:
      contents: read
      packages: write
    steps:
      - name: Checkout repository
        uses: actions/checkout@v6

      - name: Set environment variables
        run: |
          echo "IMAGE_NAME=$(echo ${{ github.repository }} | tr '[:upper:]' '[:lower:]')" >> $GITHUB_ENV
          if [[ "${{ github.ref_name }}" == "master" ]]; then
            echo "DOCKER_TAG=production" >> $GITHUB_ENV
          else
            echo "DOCKER_TAG=staging" >> $GITHUB_ENV
          fi

      - name: Setup Node.js
        uses: actions/setup-node@v6
        with:
          node-version: '24'
          cache: 'npm'

      - name: Install, Lint and Test API
        run: |
          npm ci
          npx prisma generate
          npm run lint
          npm run test

      - name: Log in to GHCR
        if: github.event_name == 'push'
        uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build and push API image
        if: github.event_name == 'push'
        uses: docker/build-push-action@v7
        with:
          context: .
          file: ./Dockerfile
          push: true
          tags: ghcr.io/${{ env.IMAGE_NAME }}:${{ env.DOCKER_TAG }}

  deploy:
    if: github.event_name == 'push'
    needs: build-and-push
    runs-on: ubuntu-24.04
    steps:
      - name: Set environment variables (CD)
        run: |
          echo "IMAGE_NAME=$(echo ${{ github.repository }} | tr '[:upper:]' '[:lower:]')" >> $GITHUB_ENV
          if [[ "${{ github.ref_name }}" == "master" ]]; then
            echo "DOCKER_TAG=production" >> $GITHUB_ENV
            echo "COMPOSE_FILE=docker-compose.prod.yml" >> $GITHUB_ENV
          else
            echo "DOCKER_TAG=staging" >> $GITHUB_ENV
            echo "COMPOSE_FILE=docker-compose.staging.yml" >> $GITHUB_ENV
          fi

      - name: Deploy to VPS via SSH
        uses: appleboy/ssh-action@v1.0.3
        with:
          host: ${{ secrets.VPS_HOST }}
          username: ${{ secrets.VPS_USERNAME }}
          key: ${{ secrets.VPS_SSH_KEY }}
          envs: IMAGE_NAME,DOCKER_TAG,COMPOSE_FILE
          script: |
            cd ~/data-skills-radar-api

            # 1. Authentification au registre GHCR depuis le VPS
            echo "${{ secrets.GITHUB_TOKEN }}" | sudo docker login ghcr.io -u ${{ github.actor }} --password-stdin

            # 2. Génération du fichier .env.<TAG> avec les seuls accès AppRole Vault
            echo "NODE_ENV=${DOCKER_TAG}" > .env.${DOCKER_TAG}
            echo "VAULT_ADDR=http://dsr-vault:8200" >> .env.${DOCKER_TAG}
            echo "ROLE_ID=${{ secrets.VAULT_ROLE_ID }}" >> .env.${DOCKER_TAG}
            echo "SECRET_ID=${{ secrets.VAULT_SECRET_ID }}" >> .env.${DOCKER_TAG}

            # 3. Téléchargement de la nouvelle image et redémarrage du conteneur
            sudo IMAGE_NAME=${IMAGE_NAME} docker compose -f ${COMPOSE_FILE} pull
            sudo IMAGE_NAME=${IMAGE_NAME} docker compose -f ${COMPOSE_FILE} up -d
```

## 🌍 3.2. Reverse Proxy (Nginx) et Sécurité SSL (HTTPS)

> **Contexte :** Mon pipeline CI/CD déploie mes conteneurs d'API en production (`127.0.0.1:3000`) et en staging (`127.0.0.1:3001`), mais le pare-feu UFW bloque ces ports depuis l'extérieur. J'ai configuré **Nginx** sur l'hôte pour écouter sur les ports `80/443` et router le trafic en fonction du sous-domaine.

### 1. Configuration des Server Blocks Nginx (`/etc/nginx/sites-available/dsr-api`)

```nginx
# 🚀 API PRODUCTION
server {
    listen 80;
    server_name api.dataskills.thomasnoel.dev;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_cache_bypass $http_upgrade;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

# 🧪 API STAGING
server {
    listen 80;
    server_name api-staging.dataskills.thomasnoel.dev;

    location / {
        proxy_pass http://127.0.0.1:3001;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_cache_bypass $http_upgrade;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

### 2. Activation de la Configuration & Sécurisation HTTPS avec Certbot

```bash
# 1. Activation du site par lien symbolique
sudo ln -s /etc/nginx/sites-available/dsr-api /etc/nginx/sites-enabled/

# 2. Vérification de la syntaxe Nginx et rechargement sans coupure
sudo nginx -t
sudo systemctl reload nginx

# 3. Génération des certificats SSL Let's Encrypt (ECDSA) et redirection HTTPS automatique
sudo certbot --nginx -d api.dataskills.thomasnoel.dev -d api-staging.dataskills.thomasnoel.dev
```
