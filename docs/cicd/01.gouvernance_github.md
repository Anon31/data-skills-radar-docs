# 🔒 1. Gouvernance GitHub, Protection des Branches (Rulesets) & Runtimes CI/CD

> **Objectif de ce chapitre :** Documenter ma politique de sécurisation Git (**GitHub Rulesets**) adaptée à la nature de chacun de mes dépôts, le paramétrage de mes verrous qualité (*Quality Gates*), l'astuce d'organisation en mode « Développeur Solo », la standardisation de mes runners sur **Ubuntu 24.04 LTS** et **Node.js 24**, ainsi que l'harmonisation de **Release Drafter**.

---

## 🎯 1. Contexte & Matrice de Gouvernance par Dépôt

Mes pipelines CI/CD déploient automatiquement mes applications en **Staging** (sur la branche `develop`) et en **Production** (sur la branche `master`). Sans garde-fou au niveau de GitHub, une simple erreur de commande locale (`git push origin master` ou `git push --force`) pourrait écraser l'historique Git ou déployer du code non testé directement sur mon serveur VPS OVH.

Plutôt que d'appliquer un dogme unique qui freinerait la rédaction documentaire, j'ai mis en place une **gouvernance pragmatique à deux niveaux** :
*   **Stricte** sur mes dépôts applicatifs et data (`data-skills-radar-api`, `data-skills-radar-app`, `data-skills-radar-lakehouse`).
*   **Allégée** sur mon portail de documentation (`data-skills-radar-docs`).

| Dépôt GitHub | Branches Protégées | Niveau de Protection | Job CI Obligatoire (*Status Check*) | Flux de Travail (*Workflow*) |
| :--- | :--- | :--- | :--- | :--- |
| **`data-skills-radar-api`** | `master`, `develop` | **Strict** (PR + CI obligatoires) | `build-and-push` (Lint + Tests Vitest + Prisma) | `feat/*` → PR → `develop` → PR → `master` |
| **`data-skills-radar-app`** | `master`, `develop` | **Strict** (PR + CI obligatoires) | `build-and-push` (Lint + Build Angular Prod) | `feat/*` → PR → `develop` → PR → `master` |
| **`data-skills-radar-lakehouse`** | `master`, `develop` | **Strict** (PR + CI obligatoires) | Validation Qualité Python / PySpark | `feat/*` → PR → `develop` → PR → `master` |
| **`data-skills-radar-docs`** | `master` | **Allégé** (Push direct autorisé) | Aucun (Déploiement continu direct) | Push direct sur `master` (anti-suppression & anti-force-push) |

## 🛡️ 2. Configuration des Règles (GitHub Rulesets)

Plutôt que les anciennes *Classic Branch Protection Rules*, j'utilise les **GitHub Rulesets** (plus modernes, cumulables et permettant de cibler plusieurs branches en une seule règle via *Settings > Rules > Rulesets > New ruleset > New branch ruleset*).

### A. Dépôts Applicatifs (`data-skills-radar-api` & `data-skills-radar-app`)

*   **Ruleset Name :** `Protection Production & Staging`
*   **Enforcement status :** `Active`
*   **Bypass list :** Vide *(aucun contournement autorisé en usage normal)*.
*   **Target branches (*Include by pattern*) :** `master` et `develop`.

**Règles (*Branch rules*) activées :**
1.  ✅ **Restrict deletions :** Interdit formellement la suppression accidentelle des branches `master` ou `develop`.
2.  ✅ **Block force pushes :** Interdit `git push --force`, garantissant l'intégrité et la traçabilité de l'historique Git.
3.  ✅ **Require a pull request before merging :**
    *   Interdit tout `git push` direct sur `master` et `develop` (ce qui garantit également le déclenchement systématique de mon `pr-labeler` et de `Release Drafter`).
    *   **Required approvals :** `0` *(voir l'encadré « Développeur Solo » ci-dessous)*.
4.  ✅ **Require status checks to pass (Verrou Qualité / *Quality Gate*) :**
    *   Vérification obligatoire du job **`build-and-push`** (issu de `.github/workflows/deploy.yml`).
    *   Option **Require branches to be up to date before merging** cochée (oblige à intégrer les derniers changements de la branche cible avant fusion).
    *   *Conséquence :* Si ESLint, un test unitaire Vitest, la génération Prisma ou le build Angular échoue sur la Pull Request, le bouton **Merge** reste grisé et bloqué par GitHub !
5.  ✅ **Require linear history :**
    *   Force l'utilisation de *Squash and merge* ou *Rebase and merge*, garantissant un historique linéaire propre et un changelog **Release Drafter** parfaitement lisible.

> [!TIP]
> **Astuce « Développeur Solo » : Pourquoi régler `Required approvals = 0` ?**  
> Sur GitHub, l'auteur d'une Pull Request **ne peut pas approuver sa propre PR**. Si je règle `Required approvals` sur `1` sans m'ajouter dans la *Bypass list*, je bloque mes propres fusions !  
> *   **En mode solo :** Je laisse `Required approvals = 0`, tout en gardant **Require a pull request** + **Require status checks (`build-and-push`)** actifs. C'est le robot CI GitHub Actions qui joue le rôle d'approbateur technique impartial.  
> *   **En équipe (entreprise) :** On passe cette valeur à `1` ou `2` avec l'option *Dismiss stale pull request approvals when new commits are pushed*.

### B. Dépôt Documentation (`data-skills-radar-docs`)

Pour éviter toute friction lors de la mise à jour quotidienne de ma documentation Docsify, j'ai créé un Ruleset minimaliste de sécurité sur `master` :
*   **Ruleset Name :** `Protection Intégrité Master`
*   **Enforcement status :** `Active`
*   **Target branches :** `master`
*   **Règles activées :**
    1.  ✅ **Restrict deletions** (Empêche la suppression de `master`).
    2.  ✅ **Block force pushes** (Empêche d'écraser l'historique documentaire).
    *   *(L'option "Require a pull request before merging" n'est volontairement pas cochée afin de conserver le confort du push direct sur `master`).*

## 🧹 3. Pragmatisme Qualité : Gérer ESLint dans les Fichiers de Tests (`*.spec.ts`)

Le verrou qualité `build-and-push` exécute `npm run lint` à chaque Pull Request. Lorsque la règle `@typescript-eslint/no-explicit-any` devient contraignante lors de l'écriture de *mocks* complexes dans les tests unitaires Vitest, il ne faut jamais désactiver le linter en CI : j'assouplis simplement cette règle de manière ciblée pour les seuls fichiers `*.spec.ts` et `*.test.ts` à la fin de `eslint.config.mjs` :

```javascript
// Extrait ajouté à la fin du tableau exporté dans eslint.config.mjs
{
  files: ['**/*.spec.ts', '**/*.test.ts'],
  rules: {
    '@typescript-eslint/no-explicit-any': 'off',
  },
}
```

Ainsi, mon code applicatif de production reste **100 % strictement typé**, tout en conservant une écriture fluide et rapide pour mes tests unitaires.

## ⚡ 4. Standardisation des Runners (`ubuntu-24.04`) & Migration vers Node.js 24

Face à la migration progressive par GitHub du label flottant `ubuntu-latest` vers Ubuntu 26.04 ([Runner Images #14748](https://github.com/actions/runner-images/issues/14748)) et à la dépréciation officielle du runtime **Node.js 20** sur les runners GitHub Actions ([Deprecation of Node 20](https://github.blog/changelog/2025-09-19-deprecation-of-node-20-on-github-actions-runners/)), j'ai standardisé l'ensemble de mes workflows :

1.  **Épinglage explicite des Runners :** Tous mes jobs CI/CD utilisent **`runs-on: ubuntu-24.04`** pour garantir des builds 100 % déterministes.
2.  **Mise à niveau des Actions vers Node.js 24 (`node24`) :**

| Action GitHub | Ancienne Version (`node20`) | Version Standardisée (`node24`) | Dépôts Concernés | Rôle Technique |
| :--- | :---: | :---: | :--- | :--- |
| **`actions/checkout`** | `@v4` | **`@v6`** | Tous (`app`, `api`, `docs`) | Récupération du code source et isolation sécurisée des identifiants Git. |
| **`actions/setup-node`** | `@v4` | **`@v6`** | `app`, `api` | Provisionnement de l'environnement Node.js `24` avec cache `npm`. |
| **`docker/login-action`** | `@v3` | **`@v4`** | `app`, `api`, `docs` | Authentification auprès du registre d'images GitHub (`ghcr.io`). |
| **`docker/build-push-action`** | `@v6` | **`@v7`** | `app`, `api`, `docs` | Construction de l'image Docker et publication sur `ghcr.io`. |
| **`release-drafter/release-drafter`** | `@v5` | **`@v7`** | Tous (`app`, `api`, `lakehouse`, `docs`) | Génération automatique des notes de version (Changelog SemVer). |

## 🏷️ 5. Harmonisation du Workflow `Release Drafter`

Maintenant que mes branches sont protégées et que mes premières releases `v0.0.1` sont publiées, j'ai configuré `.github/workflows/release-drafter.yml` sur mes dépôts multi-branches (`api` et `app`) pour qu'il ne génère le brouillon de release final que lors des fusions sur **`master`** (évitant que les merges intermédiaires sur `develop` ne déplacent la cible du brouillon hors de la branche de production) :

```yaml
name: Release Drafter

on:
  push:
    branches:
      - master

permissions:
  contents: write
  pull-requests: read

jobs:
  update_release_draft:
    runs-on: ubuntu-24.04
    steps:
      - uses: release-drafter/release-drafter@v7
        with:
          config-name: release-drafter.yml
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

## 🧪 6. Validation de la Sécurité (Test de Rejet)

Pour vérifier empiriquement que mon verrou GitHub Ruleset protège efficacement mes dépôts applicatifs (`api` et `app`), j'ai exécuté un test d'intrusion/push direct sur `master` depuis mon terminal local :

```bash
git checkout master
git commit --allow-empty -m "test(security): tentative de push direct"
git push origin master
```

**Résultat obtenu (Preuve de fonctionnement du Ruleset) :**
```text
remote: error: GH013: Repository rule violations found for refs/heads/master.
remote: - Changes must be made through a pull request.
remote: - Required status check "build-and-push" is expected.
To https://github.com/Anon31/data-skills-radar-api.git
 ! [remote rejected] master -> master (push declined due to repository rule violations)
error: failed to push some refs to 'https://github.com/Anon31/data-skills-radar-api.git'
```

*(J'ai ensuite nettoyé mon commit de test local avec `git reset --hard origin/master`).*

> **Statut :** Mes dépôts sont verrouillés avec une gouvernance équilibrée. Aucune régression ni erreur de compilation ne peut plus atteindre le VPS en Staging ou en Production sans avoir franchi avec succès le portail de la CI, tout en conservant un flux de publication fluide sur la documentation.
